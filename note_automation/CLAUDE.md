# note記事自動生成 作業指示書

ユーザーから「note記事を生成して」と言われたら、以下の手順を順番に実行すること。

---

## 前提

- 作業ディレクトリ: `note_automation/`
- 永続inputファイル（変わらない）:
  - `input/01_selling_know_how.txt` → 売れる記事のノウハウ
  - `input/04_image_style.txt` → 画像のトンマナ指定
- 素材置き場: `input/materials/`（別リポジトリ等から持ち込んだ素材の一時置き場）
- 記事ごとのinput: `input/YYYY-MM-DD/`（記事化を決めたときにユーザーが作成）
  - `02_theme.txt` → 記事テーマ
  - `03_my_info.txt` → 筆者の一次情報
- 記事ごとのoutput: `output/YYYY-MM-DD/`（記事生成時に自動作成）

---

## 手順

### ステップ0：作業フォルダの特定と my_info ドラフト生成

#### 【作業フォルダの特定】

まず `input/` フォルダを確認し、最新の日付フォルダ（例: `input/2026-03-23/`）を特定する。

- 日付フォルダがない場合は作業を中断し、ユーザーに以下を伝える：
  ```
  input/YYYY-MM-DD/ フォルダがありません。
  記事用のフォルダを作成して 02_theme.txt と 03_my_info.txt を用意してください。
  （input/materials/ に素材がある場合はそちらを参考にしてください）
  ```
- 以降の手順では、特定した日付フォルダを作業inputとして使用する

#### 【my_info ドラフト生成】

過去の会話ログ（JSONLファイル）を読み取り、`03_my_info.txt` のドラフトを作成してユーザーに提示する。

**ログファイルの場所：**
`/home/hidetada48/.claude/projects/-home-hidetada48-test/`

**手順：**
1. 上記フォルダ内の `.jsonl` ファイルの件数を確認する
   - **20件を超える場合は作業を中断し、ユーザーに「ログが〇件あります。全件読むとコンテキストが大きくなりますが続けますか？」と確認すること**
   - 20件以下であれば全件読み込む
2. `input/YYYY-MM-DD/02_theme.txt` のテーマを先に確認する
3. ログの中からテーマに関連するユーザーの発言・体験・気づき・エピソードを抽出する
4. 以下の形式でドラフトを提示し、**承認を得るまで次のステップに進まないこと**：

```
【03_my_info.txt のドラフト確認をお願いします】

## きっかけ
- 〇〇〇〇

## 体験・エピソード
- 〇〇〇〇

## 詰まったこと・工夫したこと
- 〇〇〇〇

## 感想・気づき
- 〇〇〇〇

このドラフトでよければ「OK」、修正があればご指示ください。
OKの場合、このドラフト内容を03_my_infoとして記事生成に使用します。
```

### ステップ1：インプットファイルを読み込む

#### 【画像スタイル参照ファイルのチェック】

まず `input/YYYY-MM-DD/` フォルダ内に `.png` / `.jpg` / `.jpeg` ファイルがあるか確認する。

**画像ファイルが見つかった場合：**

1. 画像を読み込み、以下の観点でスタイルを分析する（被写体・内容・テキストは無視）：
   - 背景色・グラデーション（方向・色値）
   - アクセントカラーとその使われ方
   - レンダリングスタイル（3D CG / フラット / イラスト等）
   - エフェクト（ネオングロー / パーティクル / 被写界深度等）
   - 構図・レイアウト（ゾーン分割 / 奥行き層数等）
   - タイポグラフィの体裁（フォントの重さ・サイズ比・色・配置）
   - 全体の雰囲気・密度感

2. `input/04_image_style.txt` が既に存在する場合は、上書き前にユーザーへ確認を取る：
   ```
   inputフォルダに参照画像（ファイル名）が見つかりました。
   スタイルを分析し、04_image_style.txt を上書き生成します。
   現在の04_image_style.txtは削除されます。よろしいですか？（OK / スキップ）
   ```

3. OKの場合（または04_image_style.txtが存在しない場合）、分析結果を `input/04_image_style.txt` として保存する。
   - **具体的な被写体・オブジェクト（スマートフォン等）は記録しない**
   - 色・エフェクト・レンダリング・構図・タイポグラフィの体裁のみを記録する
   - ステップ5で記事テーマに合うオブジェクトを選ぶ

**画像ファイルがない場合：** 既存の `04_image_style.txt` をそのまま使用する。

#### 【通常インプット読み込み】

以下の4ファイルを読み込む：

- `input/01_selling_know_how.txt` → 売れる記事のノウハウ
- `input/YYYY-MM-DD/02_theme.txt` → 記事テーマ（#で始まる行はコメントなので無視）
- `input/YYYY-MM-DD/03_my_info.txt` → 筆者の一次情報
- `input/04_image_style.txt` → 画像のトンマナ・スタイル指定（上記で生成済みの場合はそちらを使用）

### ステップ2：Web調査の要否を判断し、必要なら実施する

まず以下の基準でWeb調査が必要かどうかを判断し、**ユーザーに宣言してから進むこと**：

**調査不要なケース（スキップしてよい）：**
- `03_my_info.txt` に体験・エピソードが十分に書かれている
- 記事が「開発記録」「体験談」「作ってみた」系で、外部情報を補う必要がない
- Web情報を混ぜると一次情報の純度が下がると判断できる

**調査が有効なケース：**
- テーマの背景知識・統計・トレンドが必要な場合
- 読者が「なぜこれが重要か」を理解するために外部情報が役立つ場合

**宣言の例：**
- 調査する場合：「テーマの背景情報が薄いためWeb調査を行います」
- スキップする場合：「一次情報が充実しているためWeb調査はスキップします」

**調査を実施する場合：**

Jina AI MCPの検索ツールを使い、テーマに関連する情報を調査する。

- 検索キーワード例：`{テーマ} 方法 コツ 実践`
- 日本語の情報を優先する
- 5件以上の調査結果を収集する
- **調査が失敗した場合は作業を中断し、ユーザーに報告する**

### ステップ3：記事の目次を提示し、承認を得る

以下をすべて踏まえて記事構成を考える：

- 売れる記事ノウハウ（必ず全項目反映）
- 筆者の一次情報
- Web調査結果

ユーザーに以下の形式で目次を提示し、**承認を得るまで次のステップに進まないこと**：

```
【目次の確認をお願いします】

タイトル案：〇〇〇〇
想定読者：〇〇〇〇

## 見出し1
## 見出し2
## 見出し3
...

この目次でよければ「OK」、変更があればご指示ください。
```

### ステップ4：記事本文を執筆する

目次が承認されたら本文を執筆する。この時点では画像タグは挿入しない。

【執筆ルール】
1. 売れる記事ノウハウを一つ残らず反映すること
2. 筆者の一次情報を具体的なエピソードとして盛り込むこと
3. 読者が「自分のことだ」と感じられる書き出しにすること
4. 見出しは `##` を使うこと
5. 文字数は3000〜5000文字
6. note向けの読みやすい文体（短い文・改行多め）

### ステップ5：画像の提案を提示し、承認を得る

本文が完成したら、本文の構成を踏まえて画像の挿入箇所・枚数・内容を提案する。

`input/04_image_style.txt` のトンマナを踏まえて、以下の形式でユーザーに提示し、**承認を得るまで次のステップに進まないこと**：

【トンマナ統一ルール】
- `04_image_style.txt` が存在しない、または「お任せ」の場合は、全画像に共通するトンマナ（色味・画風・雰囲気）をこのステップで決定し、プランに明記すること
- 全画像を通じて統一感が保たれるよう、色調・構図・スタイルを揃えること

```
【画像プランの確認をお願いします】

合計〇枚を予定しています。

1. サムネイル（記事冒頭）
   - 内容：〇〇〇〇
   - スタイル：〇〇〇〇

2. 本文画像①（「## 見出し名」の後）
   - 内容：〇〇〇〇
   - スタイル：〇〇〇〇

...

枚数や内容を変更したい場合はご指示ください。OKであれば「OK」とお知らせください。
```

### ステップ6：本文に画像タグを挿入し、JSONファイルに書き出す

承認済みの画像プランに従い、以下の形式で本文の該当箇所に画像タグを挿入する：
- `【画像:サムネイル|説明文】` （記事冒頭）
- `【画像:本文|説明文】` （本文中、承認された箇所）

その後、`output/YYYY-MM-DD/image_prompts.json` に書き出す。（フォルダがなければ作成する）

【プロンプト生成ルール】
- `input/04_image_style.txt` のトンマナをプロンプトに必ず反映すること
- 画像内にテキスト・文字が含まれる場合は、必ず日本語フォントで表示するよう英語プロンプトに明記すること（例："if any text appears, use Japanese characters"）
- `04_image_style.txt` が存在しない、または「お任せ」の場合は、ステップ5で決定したトンマナを全プロンプトに一貫して反映し、統一感を確保すること

形式：
```json
[
  {
    "type": "thumbnail",
    "description_ja": "どんな画像か日本語で説明",
    "prompt_en": "Gemini 3.1 Flash Image向け英語プロンプト（写真調・高品質・テキストなし）",
    "aspect_ratio": "16:9"
  },
  {
    "type": "body",
    "description_ja": "どんな画像か日本語で説明",
    "prompt_en": "Gemini 3.1 Flash Image向け英語プロンプト（写真調・高品質・テキストなし）",
    "aspect_ratio": "1:1"
  }
]
```

### ステップ7：記事ファイルを保存する

`output/YYYY-MM-DD/article_YYYYMMDD_HHMMSS.md` として保存する。（フォルダがなければ作成する）

### ステップ8：画像を生成する

以下のコマンドを実行する：

```bash
python3 note_automation/generate_images.py
```

（Windowsの場合は `python` に読み替える）

### ステップ9：完了報告

以下を報告する：
- 記事ファイルのパス
- 生成された画像の一覧
- note.comへの投稿手順（貼り付け方）

## GitHubへのpush手順

ユーザーから「pushして」と言われたら、以下を実行すること。

```bash
# input・outputフォルダの変更・追加を全部ステージング
git add note_automation/input/ note_automation/output/

# コミット（日本語でわかりやすく）
git commit -m "記事と画像を更新"

# GitHubへpush
git push origin main
```

- 新規ファイルも既存ファイルの変更も、両フォルダ内のものはすべて対象になる
- `.env`（APIキー）は`.gitignore`で除外済みなので誤ってpushされる心配はない
