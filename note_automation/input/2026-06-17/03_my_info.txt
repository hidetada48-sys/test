# 筆者の一次情報

※業種が特定される固有名詞（製紙・古紙・パルプ・抄紙機・トイレットペーパー・製品名など）は
　記事化のときに必ず一般化すること。ここでは素材として実態を書いておく。

## きっかけ・背景
- 地方の中小メーカー（社員35名・創業60年超）の経営幹部から業務支援を頼まれた
- その人は生産段取り・仕入交渉・顧客折衝・労務・総務を**たった一人で担っている**
- 情報管理は「ほぼ頭の中（手帳と記憶）」だった
- 販売管理システムはあるが、CSVを出せるだけで活用できていなかった
- 「3ヶ月後にどうなっていたい？」と聞いたら、こう答えた：
  「過去の経緯がすぐ引き出せる／販売データで打ち手が見える／業務がテンポよく回る／定期的に業界情報が入ってくる」

## 作ったものの全体像：7人の「参謀」
- Claude Code 上に、業務領域ごとの専門家AIを「参謀（さんぼう）」として複数構築している
- 設計思想は「経営参謀を頂点に、6つの専門参謀が並ぶ階層構造」
- 全参謀のスキル・データ・ナレッジは git リポジトリ1つに収まっている
- 起点はすべて「話しかけるだけ」（記録・想起・収集にファイル操作は不要）

### 参謀の一覧（7人）
```
経営参謀 ← 全参謀を統括・大局的に判断する
├── 業界参謀   （業界動向・相場・競合）
├── 取引先参謀 （取引先との折衝記録・経緯管理）
├── 販売参謀   （販売実績の分析・打ち手提案）
├── 現場参謀   （生産管理・設備・工程知識）
├── 経理参謀   （決算分析・月次収支）
└── 労務参謀   （労務データ・期限アラート）
```

## 各参謀の現状（正直に書く：完成度はバラバラ）

### 業界参謀【稼働中】
- 毎週はじめの起動時に、主要原材料の相場・燃料価格・法規制・競合動向などを自動収集
- Jina AI MCP（AIがWeb検索するための仕組み）で調べ、markdownレポートを生成 → gitにpush
- 別PC（Windows）でもgit pullするだけで最新レポートが届く
- 実際にキャッチした情報例：「主要原材料の卸値が約2年半ぶりに上昇」「関連する法改正（2026施行）で委託契約の見直しが必要になる可能性」
- 当初は週次の自動スケジュール実行だったが、「起動時にその週のレポートが無ければ作る」方式に作り直した（PC2台での二重生成・取り込み漏れを防ぐため）

### 取引先参謀【稼働中】
- 取引先45社との折衝記録を管理
- 使い方：「○○社から値上げの問い合わせがあって、年間契約の対象外商品は値上げ了承になった」と話すだけ → Claudeが整形して保存
- 「○○社の未対応アクションは？」と聞けば一覧で出る
- 実際の用途：全顧客45社への一斉値上げ交渉の折衝経緯をリアルタイムで追跡中
- 工夫：取引先名にWindowsで使えない文字（\ / : * ? " < > |）が混じるとフォルダ作成に失敗するので、登録時に全角化・除去するルールを入れた

### 販売参謀【稼働中】
- 販売管理システムからCSVを書き出してドライブに置くだけで、月次分析Excelを自動生成
- Excelの中身：①月別集計＋前年比 ②推移グラフ ③上半期・下半期比較 ④今月の異変（急落・急増・消滅・新規・発注リズムの乱れを自動検出）⑤総括コメント
- Claude Code自身（Python / openpyxl）がExcelを直接組み立てる。人の手はゼロ
- 最初は1社専用のハードコードだったが、全得意先に横展開した（ファイル名ではなくCSVの中身から得意先・年度を判定）
- 実際の成果：ある得意先の今年度トータルが金額+8.0%・数量+6.0%、ある主力商品が前年比+34.2%で全体を牽引していたことを自動で発見
- ハマった点：「Excelのグラフが真っ白になる問題」。非表示セルを参照するとグラフが描画されない仕様だったので、グラフ用データを別の隠しシートに逃がして解決した

### 現場参謀【話しかけ記録ベースで運用中・専用スキルは未実装】
- まだ専用の自動化スキルは作っていないが、「話しかけて記録」する形ですでに使っている
- 例：主力設備が突発故障し、約45時間（実生産ロス）止まったトラブルの経緯を時系列で記録
- 設備の異音・速度のばらつきなど「故障の予兆」も記録し、点検・予防交換の判断材料にしている

### 経理参謀【構想中】
- 決算資料が揃ったら着手予定。月次収支サマリ・経年分析を担当させる

### 労務参謀【実装が一番進んでいる・多機能】
- 有給休暇の一斉付与アラート：全社員の付与日数を起動時に自動計算して一覧表示（入社月に応じた按分計算つき）
- 年次イベントの自動通知（9件）：出勤カレンダー作成・36協定更新・住民税通知・人事考課（夏冬）・労働保険年度更新・算定基礎届・年末調整など。「対応開始」日を過ぎたら、処理済みと言うまで一覧に出続ける
- 法改正の月次監視：労務関連の法改正を自動でWeb調査。「法律が変わりました」で終わらせず「自社への影響はこれです」まで翻訳して通知する
- 労災対応の仕組み：労災発生時の届出（死傷病報告など）の下書きをClaudeが作る。ここで大失敗の教訓あり（下記エピソード参照）

### 経営参謀【構想中・頂点】
- 他の参謀のデータが溜まってから実装する予定
- 役割：複数の参謀にまたがる判断を、全参謀の要約（SUMMARY）を横断して大局的にアドバイスする

## 土台となる3層アーキテクチャ
1. Git／フォルダ：すべての記録の永続保存・バージョン管理
2. basic-memory：セッションをまたいだ記憶の検索。「○○社との経緯は？」で過去を即座に引き出す
3. NotebookLM：大量の文書（業界資料・規定など）の深掘り分析

## 作る途中で起きたこと（エピソード）

### ① CLAUDE.mdに書いても守られない → フックで物理的に強制した
- 「セッション開始時にgit pullせよ」と指示書（CLAUDE.md）に書いたが、Claudeが毎回スキップした
- テキストで書いたルールはClaudeの注意力頼みで、実行を保証しない
- そこで「起動時に自動で走るスクリプト（SessionStartフック）」で機械的に強制した
- 同じ問題が何度も起きて、最終的に「文章のルール → フックで機械保証」という方針に統一した
- 巨大ファイルを丸ごと読んで固まる事故も、PreToolUseフックで物理的にブロックした

### ② 毎ターン38秒フリーズした真因は自動バックアップだった
- Claudeが返答するたびに約38秒フリーズする症状が続いた
- 3日間「起動が重いのでは」と思い込み、起動まわりの対策ばかり打って外し続けた
- 真因は「応答のたびに毎回発火する設定（Stopフック）にクラウドへのバックアップ処理をぶら下げていた」こと
- 記録ノートが増えてAPIの制限に当たり、リトライ待ちで38秒に膨らんでいた
- 「毎ターン実行（Stop）」と「セッション終了時に実行（SessionEnd）」のフックを混同していた設計ミスが根本
- 終了時だけ走るように直して解決

### ③ 公的手続きを「調べずに」設計して作り直しになった（労災対応）
- 労災の届出を、未検証の前提（古い方式）で設計し始めた
- 経営幹部から「設計が甘い。最初から調べてから作れ」と指摘された
- 厚労省の公式資料を読み直したら、提出ルートが想定と違っていて設計を組み直すことに
- 教訓：公的手続きが絡む仕組みは、設計の前に必ず官公庁の一次情報で裏取りする

### ④ Windows / Linux の両方で動かす難しさ
- 開発はLinux、実際の業務はWindowsという2環境
- `python3`がWindowsではMicrosoft Storeの「偽物（スタブ）」で、呼ぶと失敗する
- `grep`の出力にWindowsでは改行コードが混入して比較処理が壊れる
- 対策：スクリプトの入口でpython3／python／pyを順に試し、本物だけを実行する定石を確立した
