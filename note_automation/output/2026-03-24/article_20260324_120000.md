# Claude Code × Playwright × NotebookLM。Xブックマークを資産に変えるスキルを作った

【画像:サムネイル|Xブックマーク→Claude Code→NotebookLMへ繋がるフロー。ダークテック×ネオングロー系サムネイル】

---

## Xのブックマーク、ちゃんと使えてますか？

正直に言います。

私のXのブックマーク、数百件溜まっていました。

「あとで読もう」と思ってブックマークしたツイート。
「これは使えそう」と思って保存した記事のリンク。
「このコード参考にしたい」と思って押したブックマーク。

全部、眠ったまま。

見返したのは保存した直後だけ。
検索しようにも、Xのブックマーク検索は使いづらい。
気づいたら「溜めているだけの場所」になっていました。

同じ経験、ありませんか？

ブックマークって本来、自分が価値を感じた情報の集積場のはずです。
それが活用できていないのは、もったいないを通り越してもはや損失です。

そこで考えました。

**NotebookLMのソースにできないか？**

NotebookLMは、ドキュメントを読み込ませることで、それを知識ベースとして質問できるGoogleのAIツールです。PDFでも、テキストでも、Google Driveのファイルでも読み込める。

「ブックマークをテキストにしてGoogle Driveに置けば、NotebookLMで使えるんじゃないか？」

そう気づいたとき、このツールを作ることにしました。

---

## 作ったもの：slash command1発でNotebookLMへ同期するClaude Codeスキル

### Claude Codeの「スキル」として実装したのが最大のポイント

このツールの一番の特徴は、**Claude Codeのスキルとして実装している**ことです。

Claude Codeには「スキル」という仕組みがあります。
SKILL.mdというファイルに手順を書いておくだけで、
スラッシュコマンドとして呼び出せるようになります。

つまり、Claude Codeのターミナルで

```
/x-bookmark-to-notebooklm
```

と打つだけで、ブックマークの取得からGoogle Driveへのアップロードまで全部動く。

コマンドを覚える必要はありません。
スクリプトの場所を探す必要もありません。
Claude Codeを開いて、スラッシュを打てばいい。

これがスキル化の強さです。

【画像:本文|X→Playwright→テキストファイル→Google Drive→NotebookLMの処理フローをノードと発光ラインで視覚化】

### ツール全体の流れ

フローはシンプルです。

```
① Claude Codeで /x-bookmark-to-notebooklm を実行
② PlaywrightがヘッドレスブラウザでXにアクセス
③ ブックマーク一覧をスクロールしてURLを収集（フェーズ1）
④ 各ツイートのページを開いて全文を取得（フェーズ2）
⑤ テキストファイルとして保存
⑥ rcloneでGoogle Drive（X-Bookmarks-NotebookLMフォルダ）へアップロード
⑦ NotebookLMでそのフォルダを参照 → 検索・質問できる
```

NotebookLM側は最初に一度だけフォルダを追加する設定をすればOKです。
以降は⑦のステップは不要で、自動的に最新のファイルが反映されます。

### 一度だけログイン、あとはヘッドレス

Xへのログインは最初に一度だけ行います。

`save_session.py` を使って、GUIのブラウザでXにログイン。
このとき認証情報（クッキー）がファイルに保存されます。

次回以降は、このクッキーを読み込んでヘッドレス（画面なし）で動作します。
コマンドを叩くだけで、ブラウザが起動していなくてもXにアクセスできる。

パスワードを毎回入力する必要もなければ、
ブラウザを手動で開く必要もありません。

## このツール、何が取れるのか

### 5パターン全対応

Xには実はいくつかのコンテンツ形式があります。
このツールは以下の5パターン全てに対応しています。

| パターン | 取得状況 |
|---|---|
| 通常ツイート | ✅ |
| X長文記事 | ✅ |
| 通常ツイート ＋ 引用通常ツイート | ✅ |
| 通常ツイート ＋ 引用X記事 | ✅ |
| 通常ツイート ＋ 外部リンクカード | ✅ |

noteの記事リンクが貼ってあるツイートも、
Qiitaの技術記事リンクが貼ってあるツイートも、
外部ページの本文（最大5000文字）まで取得します。

ブックマークした理由が「リンク先の内容が良かったから」だとしても、ちゃんと取れます。

### X長文記事は35,803文字

Xには長文記事（X Article）という形式があります。
普通のツイートとは全く異なる、数万文字になることもある記事形式です。

このツールで取得してみたとき、1件で**35,803文字**でした。

通常ツイートが140文字であることを考えると、ケタが違います。
これがNotebookLMの知識ベースに入るわけです。

### 引用ツイートの中身まで丸ごと取得

引用ツイートも、引用元の内容ごと保存されます。

実際のファイルにはこんな構造で保存されます：

```
[投稿者] @example
[日時] 2026-03-15 10:30
[URL] https://x.com/...

これは必読です。Claude Codeのセキュリティ設定について
まとまった記事です。

--- 引用ツイート (https://x.com/...) ---
[引用元の全文がここに入る]
リプライ: 36 / リツイート: 434 / いいね: 3,703 / 閲覧: 311万

```

エンゲージメント数（リツイート数・いいね数）まで保存されています。

NotebookLMに「バズっていた記事を教えて」と聞けば、
この数字を根拠に答えてくれるようになります。

【画像:本文|構造化されたブックマークテキストファイルの中身イメージ。引用ツイートのエンゲージメント数がゴールドのデータラインで光る】

実際に、あるブックマークを取得したとき、
引用元に **Claude Codeのセキュリティ設定に関する4,000字超えの解説記事** が丸ごと入っていました。

ツイート自体は短い紹介文でしたが、引用先の技術記事が完全に取得できていた。
これを見たとき「ちゃんと使えるツールになった」と確信しました。

### 「もっと見る」も自動で展開

Xでは長いツイートが「もっと見る」で省略されることがあります。
このツールは「もっと見る」ボタンを自動でクリックして、省略なく全文を取得します。

手動でやっていたらひとつひとつクリックが必要ですが、全自動です。

### 速度も問題なし

初回動作確認時の実績：
**50件・14.6KiB・19秒でGoogle Driveへアップロード完了。**

実用上、待ち時間を感じるようなストレスはありません。

## デバッグ地獄：バグとの戦いを全部話す

【画像:本文|赤いエラー表示が画面を覆い、コードが散乱するデバッグ地獄のイメージ。レッドグロー強め】

ここからが本題です。

完成形だけ見るとシンプルに見えるツールですが、
開発中はバグの連続でした。

7日間、毎日何かが壊れていました。

### バグ①：長文が途中で切れる

最初の実装では、ブックマーク一覧ページをスクロールしながらツイートのテキストを取得していました。

動いた。でも、長文が途中で切れる。

一覧ページでは「続きを読む」で省略されているため、
表示されている文字しか取れないんです。

解決策は**2フェーズアーキテクチャ**への変更でした。

- **フェーズ1**：ブックマーク一覧をスクロールして、URLだけ収集する
- **フェーズ2**：収集したURLを一件ずつ開いて、詳細ページから全文を取得する

一覧で取ろうとするから切れる。
ならば、各ページを個別に開けばいい。

シンプルな発想でしたが、これで長文問題は完全に解決しました。

### バグ②：スクリプトは正常終了なのにファイルが空

2フェーズにして動かしてみたら、今度は別の問題が起きました。

スクリプトは「成功」と言って終了している。
でも保存されたファイルを開くと、**本文が空。**

エラーも出ていない。
処理は完了している。
でも中身がない。

何が起きているのか全くわかりませんでした。

原因は「ページは表示されたけど、要素がまだDOMに出現していない」というタイミング問題でした。

Xのページは読み込み完了後も、JavaScriptが非同期でコンテンツを描画します。
「ページが開いた」≠「テキストが取れる状態になった」だったんです。

解決策は `wait_for_selector` で要素が出現するまで最大15秒待機すること。
さらに2秒の安定化待機を追加しました。

これで空ファイル問題は解消。

### バグ③：@daifukujinjiが消えた日

ある日、スクリプトが取得してきたブックマークを確認していて、おかしいことに気づきました。

「6番目のブックマークは@daifukujinjiのツイートのはずなのに、@izutorishimaが来ている。」

手動で確認すると、確かに6番目は@daifukujinjiです。
でもスクリプトは違う人のツイートを6番目として取得していた。

つまり、ツイートが「取りこぼされて」いた。

原因はXの**DOM仮想化**という仕組みでした。

Xはパフォーマンスのために、画面に表示されていない要素をDOMから削除します。
`page.keyboard.press('End')` で一気に最下部までスクロールすると、
中間のツイートが画面外になった瞬間DOMから消えてしまう。

修正は `window.scrollBy` を使って、
**0.8画面分ずつゆっくりスクロール** する方式への変更でした。

これで@daifukujinjiも正しく取れるようになりました。

### バグ④：「削除済み」だと思っていたらX記事だった

ある取得結果を見ていて、「このツイート削除されたのかな？」と思ったものがありました。

テキストが取れていない。
でも、URLにアクセスするとちゃんとページがある。

実は、**X長文記事（X Article）**だったんです。

通常ツイートは `[data-testid="tweetText"]` というセレクタで取れます。
でもX記事はそのセレクタが存在しない、全く別の構造をしています。

「削除済み」どころか、数万文字の記事が眠っていた。

解決策は2段階フォールバック：
1. まず通常ツイートのセレクタで試みる
2. 失敗したら `article.innerText` で記事全体を取得する

これにより、通常ツイートとX記事を自動判別して両方取れるようになりました。

### バグ⑤：成功率50%の壁

2フェーズ実装直後のテストで、2件中1件しかテキストが取れませんでした。

成功率50%。

原因として疑ったのは、Xのスクレイピング検知・レート制限でした。
連続してアクセスすると、Xがbot判定してコンテンツを返さなくなる可能性があります。

対策として各ツイートへのアクセスに**2秒間隔**を設けました。

急いで取得しようとするより、人間に近いペースでアクセスする。
この対策が効いたのか、その後の成功率は大きく改善しました。

### バグ⑥：コードは正しいはずなのに引用ツイートが全27ファイルで0件

これが一番頭を抱えたバグです。

コードを読んだ限りでは、引用ツイートの取得は実装されている。
ロジックも合っている。

なのに保存済みの全27ファイルを調べたら、
**引用ツイートのマーカーが1件もない。**

「コードは正しいのに動いていない」という状況は、
「コードが間違っている」よりデバッグが難しい。

原因は保存フォーマットの問題でした。
コードは引用ツイートを取得できていたのですが、
保存時のフォーマット（マーカーの書き方）が想定と異なっていたため、
後から検索しても見つからなかったんです。

コード分析と実データの検証を分けてやること。
当たり前のことですが、改めて痛感しました。

## 完成して変わったこと

7日間のデバッグを経て、ツールが完成しました。

最終的な動作確認では、

- 17件のブックマークを段階的スクロールで漏れなく取得
- 各ツイートの詳細ページから本文・引用ツイート・外部リンクを抽出
- Google Drive（X-Bookmarks-NotebookLMフォルダ）へアップロード完了

まで、問題なく通りました。

---

変わったことを正直に言うと、**ブックマークする行動の質が変わりました。**

以前は「なんとなく良さそうだからブックマーク」でした。
でも今は「NotebookLMに入れる価値があるかどうか」を考えてブックマークするようになっています。

溜めるだけだったものが、自分の知識ベースとして機能するようになると、
ブックマークの意味が変わります。

NotebookLMに「最近ブックマークした中でClaude Codeに関する情報をまとめて」と聞くと、
自分がここ数週間で集めた情報を横断して答えてくれます。

Xで見かけた記事、引用ツイートで発見した技術記事、外部リンクの内容——
全部が一つの知識ベースに集まっている。

ブックマークがついに「資産」になった瞬間でした。
